Help

Configuration Outline

Build the settings structure

Click a type to add it to the active section, or drag it directly into a target section. Selecting an item activates the section containing it. While dragging, moving near the top or bottom edge scrolls the page automatically.

Dropping on the canvas background moves an existing item back to the root. Empty builder and inspector areas intentionally contain no instructional text so the workspace stays as large as possible.

Button (Impulse) creates a real RML mod-menu button. Its menu label and button text are editable independently. After packing, the matching Start / Configuration output is a direct Impulse and can connect to every compatible impulse input.

Inline row is a real Outline container. Drag two or more ordinary settings, buttons, Runtime Displays or dynamic controls into it to place them side by side. Its own horizontal overflow is an automatic scroll layer, so the existing Ctrl/Command + Wheel hierarchy and Shift + Wheel horizontal scrolling work without a special mode. Select the row to choose its default horizontal or vertical orientation. The row's own Internal / hidden property hides the complete group by default while keeping it available to runtime Set Configuration Visibility logic. Select any direct child to define its width percentage and optionally hide its left-side label. Preview, the generated RML menu and runtime graph overrides all use the same values.

Structure

Section enums

A Section enum is an enum controller whose values become visible settings pages. Section enums can be nested. Their sections can be reordered horizontally and moved between containers.

Properties

Settings and runtime behavior

The Properties panel edits the selected item. Section enums normally use Stored only, because RML already handles their navigation. Numeric range validation can require a maximum value and enables the scalar slider. Hidden settings remain stored in the configuration even when they are not editable in the RML UI.

Vector editors use one field per component. List-style editors use one value per line where applicable.

Typed runtime graph

Pack into Node

Pack into Node replaces the visual configuration outline with an automatically synchronized typed runtime graph. Returning to the outline preserves the packed graph. Reloading restores the last open Outline or Typed Runtime Graph view together with its saved nodes and wires.

The same canvas can temporarily show an embedded Custom C# editor, a Custom C# File Graph or an API Composite's internal API & Logic Graph. In a nested view the main arrow returns to the immediately previous graph; in the main Runtime Graph it returns to Configuration Outline. The return entry is consumed once so repeated transitions cannot form a navigation loop.

A responsive graph hierarchy trail remains visible above the graph and the embedded code editor. It shows every active level from Runtime Graph through API & Logic and Custom C# File contexts to the current editor. The current level is highlighted; click any existing ancestor to return directly while all skipped child graphs are saved and closed in order. Missing graph owners, invalid API Composites and navigation cycles are never bypassed. On narrow screens the complete trail scrolls horizontally and keeps the active level in view.

The Generated file selector is available in both Configuration Outline and Typed Runtime Graph. Both views expose the same live generated project manifest, but keep independent selections: the Outline defaults to the main configuration/mod source, while the graph defaults to its generated runtime-graph source. The selector updates automatically when graph nodes add, remove or rename generated outputs.

Settings preview

Preview behavior

Preview changes remain session-local until applied or saved. The Full Color Picker keeps its profile and strength behavior. The adaptive color-picker fit script is loaded only on viewports that need it.

Pressing an Outline Button in Preview runs the connected typed impulse path locally. Preview-safe Configuration Menu nodes immediately update visibility, order, value, Inline Row direction, child width and label visibility in this Preview. Branch, Gate, Sequence and ordinary single-output impulse forwarding are simulated; runtime-only API side effects are skipped. This never invokes the generated mod and never sends anything to Resonite.

Local data

Projects, autosave and privacy

The current draft is saved automatically in this browser. Save Project creates a portable GZIP backup. Import accepts complete Builder projects and Saved API Composites as JSON or GZIP. The builder runs entirely in the browser; source code and configuration data are not uploaded.

Generated project

Export Project

Generated projects target .NET 10 for the current Resonite/RML setup. The Resonite installation path is used for local assembly references. MSBuild variables such as $(HOME) are supported, and ResonitePath can still be overridden when building.

Multiple selected files are bundled into one ZIP. When an early Harmony patch library is present, the ZIP contains separate Mod and Patches project folders plus build scripts. Their project files deploy the compiled DLLs to rml_mods and rml_libs respectively. The Export dialog renders the exact live package manifest rather than a hard-coded list, so later generator extensions appear automatically. Saved API Composites use their own export controls and are not exported through the main Export Project button.

Interactive onboarding

Guided first-steps tour

The Tour button starts the same visual assistant that appears on the first launch. Every lesson is explained in the Step Overlay first; only Demonstrate starts one teacher-mouse run, and Replay repeats it deliberately. The assistant uses the real Outline, graph, scroll, zoom, Project, Export Project and Help controls, keeps the demonstrated subject visible on the current screen size and restores the snapshotted builder state when you finish or skip it.

Node library

Browsable and searchable API catalog

Every live Resonite API category and its complete count is always listed in the Node Library and starts collapsed. Opening a category creates its node cards in bounded batches instead of mounting the complete catalog at once. Enter at least two characters in Node Search for the fastest direct lookup. Search results are capped; refine broad searches when necessary.

Typed connections

Configuration sockets and wires

● Stored value ▶ Startup ■ Saved ◆ Startup + saved ⚡ Button press impulse

Wire colors represent value types. Startup and Saved configuration sockets can connect to matching value inputs and impulse inputs; Stored sockets remain value-only. Incompatible sockets are disabled while a connection is being created.

A Button socket is already an Impulse source: each press in the RML configuration page emits exactly one pulse. It does not depend on Save Settings and does not use Startup/Saved reaction modes.

Dropping an output wire on empty graph space creates a monitor. Dropping a value-input wire can create a self-contained constant or context source. Impulse inputs and multi-input runtime operations must be connected explicitly.

Scanner runtime bridge

Live Display Value and Display Impulse

Display Value and Display Impulse prefer values published by the matching generated mod running inside Resonite. The generated runtime discovers the scanner mod without a compile-time dependency, and the scanner streams each monitor update to this builder over its local loopback SSE bridge.

Matching uses the generated namespace/class channel plus the stable graph node id. After adding, deleting or replacing a monitor, rebuild and reload the generated mod. When the scanner or matching mod is unavailable, the node clearly falls back to Runtime Only and keeps the existing local graph preview where that value can be evaluated safely.

Add Display Value (RML Menu) in Configuration Outline, then pack the outline. That item appears as its own dedicated output on the Start node. Every graph Display Value has a second RML Menu input. One Start-node display output may fan out to multiple Display Value or Display Impulse nodes. Display Impulse has the same optional RML Menu input and contributes its live pulse counter. By default, every connected runtime value stays side by side in one single RML menu row; the row does not wrap values into a vertical list. Select the Display Value (RML Menu) item in Properties to set their left-to-right order. If a vertical list is actually wanted, enable Stack values vertically there; the same order controls top-to-bottom placement in that mode. The graph wires define membership and the inspector defines presentation—there is no source dropdown.

Typed collections

For Each, Collect To List and indexed access

For Each accepts any scanner-derived or built-in type that implements System.Collections.IEnumerable. Its collection and item generics are linked: connecting a typed collection automatically infers the exact element type, while the zero-based Index and current Item remain valid for the duration of each Body impulse. Completed fires after the final item and also for empty or null collections. Reusing the same scanner API property or field output several times in one condition keeps every null-safe member read in its own expression scope, so generated C# never redeclares an API target local variable.

Example: Focused World → Get · World.AllUsers → For Each, then connect Item to a User property such as Get · User.UserName and run logging or other logic from Body. Arrays, generic lists, dictionary key/value collections and custom catalog types implementing IEnumerable<T> use the same node. Asynchronous enumerables are intentionally separate and are not executed by this synchronous node.

Get Item At Index reads one zero-based item from any synchronous typed collection. Its Collection and Item generics are linked exactly, so List<User> produces User and List<string> produces string. Item returns the type default for an invalid index, while Success reports validity and Count exposes the current collection size.

Collect To List is a separate stateful collection node. Reset clears its strongly typed List<T>, Add appends the current Value, and the List and Count outputs expose the complete current result. For a fresh scan, connect the trigger to Reset, Reset Done to For Each.Call, For Each.Body to Add, and the per-item mapped value to Value. The List output can feed Display Value, another For Each node, object inputs and compatible standard .NET collection-interface inputs. If one impulse output fans out to several direct Reset or Add targets, the generated runtime performs every direct sibling mutation first and only then follows their Reset Done / Added continuation paths. A later sibling reset therefore cannot erase values produced by an earlier continuation loop.

Dynamic configuration controls

Collection-backed controls from the runtime graph

Mark as Editable on Collect To List exposes a generated Dynamic Choice entry in the Configuration Outline node palette. It does not insert a setting merely when enabled. If it is later switched back to false, any Dynamic Choice previously materialized from that exact collection is removed from Configuration Outline automatically, because the collection is no longer an editable RML source.

Click or drag that generated palette node into the exact Outline position you want. Only then is the dynamic setting created and, after packing, exposed on the Start / Configuration node. The Dynamic Choice binds directly to the marked Collect To List source: no Display Value/helper node and no separate Labels/Stable Values source selection is required. Because that collection exists only at runtime, Properties only offers a Default selection while the matching generated mod is actually running and its runtime list is available. The Builder subscribes to that runtime channel directly, so Properties and Preview update as soon as the list arrives or changes; no unrelated click or rerender is required. Without an explicit valid default, the first runtime item is selected automatically (unless Allow empty selection is enabled). The generated Start-node string output resolves to that same effective selection as soon as the collection changes, so graph logic never remains on an empty raw configuration value while the menu already shows a valid first item. It can be wired freely into Equal, Select, Branch/flow logic, method calls, stores, or any other compatible typed runtime logic. Dynamic controls retain their exact global Configuration Outline position among ordinary settings and Runtime Display rows.

Graph interaction

Move, resize and route

Drag nodes to move them. Resize from the right edge, bottom edge or lower-right corner. Double-click a resize grip to reset that axis. Wires can contain movable bend points and branches. The graph toolbar can center the graph or clear operator nodes while retaining the packed configuration node.

Node, wire, route-point and Composite actions in Properties use one consistent square icon size. Their symbols and accent colors identify the action type without changing its behavior. Hover an icon or focus it with the keyboard to see its complete action name and explanation, such as Edit Internal API & Logic Graph; screen readers receive the same name through the button label. Destructive actions remain visually distinct: deleting a saved Composite template, a placed node, a wire or a route point never shares the same symbol. Dynamic actions update their icon, tooltip, color, ARIA name and busy state immediately when the underlying node changes; the Properties fields and their focus are not rerendered. For example, Open Node Graph switches atomically to Optimize & Open Node Graph while Source is edited and switches back as soon as synchronization completes. The same live binding applies to Custom C# File nodes directly in the Runtime Graph and inside an API Composite's internal graph.

Explicit scroll-layer selection works throughout the whole builder, not only inside the runtime graph. Hold Ctrl (Command on macOS) and use the wheel to choose a level. The hierarchy is captured from the first gesture and remains frozen while the modifier is held: moving the mouse into Properties, Generated Project Files, another node or a dialog does not replace that hierarchy. A new session starts at the outermost available level. From there, the selectable hierarchy follows visual reading order: the real visual hierarchy: each parent is visited before its descendants. Sibling or independent regions are read top to bottom and, when they share a row, left to right. A region is completed depth-first before the selector moves to a later sibling region below. Wheel down advances through that order and Wheel up walks it backward. The selector has no hard beginning or end: continuing in the same direction wraps around to the opposite end and repeats the hierarchy. The currently previewed boundary itself glows; no separate corner status box is shown. Releasing the modifier enables a global scroll override. Every subsequent Wheel event is captured before nested panels and native browser scrolling, and is routed only to the locked level regardless of cursor position. Shift does not release the selection/override only when that exact selected level has a real horizontal scroll axis; Shift + Wheel then scrolls that same level horizontally. On a level without horizontal scrolling, Shift releases the selection/override like any other non-Ctrl/Command key. Any other key (including Tab, Escape, Enter, arrows or text input) and any pointer press (mouse, touch or pen; any mouse button) releases it without consuming the original input. Reaching an edge, becoming empty, or being temporarily rerendered never silently transfers scrolling to another level. Only layers with a genuinely visible, unobscured area participate: elements outside the viewport or fully covered by a higher stacking layer (for example underneath the sticky header, a dialog or an overlay) are excluded. Partially covered layers remain selectable through their still-visible area.

The final outermost level is always the actual <html> element. Inside the Typed Runtime Graph the virtual Graph ROOT therefore appears one level before <html>, rather than replacing the page root. The <html> level remains selectable even when it has no overflow; in that case it is shown as an empty level. If a browser uses a different document.scrollingElement, that real document scroll surface is inserted immediately inside the still-present empty <html> level.

The level list is not a hard-coded set of panels. A new selection session is built from the current composed DOM path and real overflow dimensions, then locked by stable identities so dynamically rerendered elements can rebind without changing the chosen level. Dynamically rendered nested Section enums, real scrollable graph-node bodies, dialog lists and future scroll containers therefore participate automatically. A future custom surface can also declare data-rml-scroll-layer="auto" (or "always" for an intentionally selectable empty level) and a stable data-rml-scroll-layer-key without changing the selector.

Reusable API & logic graphs

API Composites and Saved API Composites

Select at least two compatible graph nodes with Ctrl/Command-click, including at least one verified scanner-catalog API node, then choose Create API Composite in Properties. The Composite keeps node placement, typed contracts, wires, bend points and branches. Open Edit Internal API & Logic Graph to continue editing it; unconnected ports of newly added internal nodes are exposed on the outer Composite automatically. Expose unconnected ports appears only while the selected node really has an eligible unconnected port that is not exposed yet. If every internal node is removed, Back still returns safely to the Runtime Graph; the empty Composite remains editable but cannot be saved or exported until a verified catalog API node is restored.

The internal graph accepts verified API nodes, supported value, math, conversion, flow and output nodes, plus the same hybrid Custom C#, C# Project and C# Reference nodes used in the Runtime Graph. Custom C# keeps one palette node with File, Action, Expression, Runtime Graph Member and Main Mod Member modes; no redundant mode-specific palette copies are created. Roslyn syntax, token, trivia and Custom C# File Output nodes remain exclusive to a Custom C# File Graph.

Use Save Composite, Update or Save New to reuse the complete internal graph. Saved Composites can be inserted from the Node Library, unpacked, deleted, exported and imported as JSON, and are checked individually against the active verified catalog. Saving and importing preserve the outer Composite's switched port side as well as every internal node's port side. Every Saved Composite carries a content fingerprint derived from its normalized name, port order and side, complete node content and layout, connections, wire routes, branch routes and owned Custom C# graphs. A different name therefore creates a new Composite. An exact normalized name plus a changed fingerprint is offered as an update; an equal fingerprint remains unchanged. In Node Actions, Save Composite appears only for an unsaved Composite, while Update appears only when the linked placed graph differs from its Saved Composite. If both fingerprints match, neither action is rendered; Save New remains available for a linked Composite. Legacy Composite JSON without a fingerprint is offered once by exact normalized name and receives its generated fingerprint when the update is accepted. Import scope follows the matching name across both locations: a Graph-only match updates only the placed graph and creates no Saved entry; a Saved-only match updates only the library; a match in both locations updates both; only a name found nowhere is imported as new. Existing duplicate Saved entries with that exact normalized name are consolidated into one retained identity during the confirmed update. A stale or orphaned Saved-Composite identity on a placed instance never blocks the name match. An open matching Composite is replaced in place and remains open. Every graph replacement preserves position and every compatible external wire route. Updating placed graphs is intentionally available only from the matching Saved Composite's circular-arrow action in the Node Library. That action is not rendered at all while every matching placed graph has the same content fingerprint; it appears only when at least one matching graph actually differs. Removed or ambiguous ports are counted before confirmation instead of being silently rewired. Every Properties action button is re-evaluated immediately after its synchronous or asynchronous action completes. State-dependent actions such as Expose unconnected ports, Update and Optimize & Open therefore appear, change or disappear without selecting the node again. Existing placed instances remain complete when a library template is deleted. Owned Custom C# File Graphs and their source are included in project save, Composite save, export, import, unpacking, migration and generated-code expansion.

Custom C# workbench

Embedded editor, floating overlay and node insertion

Opening a Custom C# code field first shows the large editor embedded in place of the current graph. The main back-arrow returns to the immediately previous graph; from the main Runtime Graph it returns to Configuration Outline. Each return entry is consumed once, so opening nested graphs and editors cannot create a closed navigation loop. Any action that replaces a Runtime Graph also replaces an embedded editor in the same way, and returning restores the correct previous view.

Only the embedded editor shows the JavaScript presentation dropdown used throughout the Builder. It contains exactly the two destinations Overlay and Separate Window; Embedded is the current view and is therefore not listed as a destination. Overlay keeps the movable application window with Return to embedded editor, Minimize/Restore, Maximize/Restore and Close in its title bar. Separate Window always opens a real native browser popup in Chromium, Firefox and Safari so the editor can be placed on another monitor. Its single operating-system/browser title bar is the only place for Minimize, Maximize/Restore and Close; the editor draws no duplicate window controls and never simulates maximization by resizing itself. The editor header adds only Return to embedded editor. Source, diagnostics, selection and the Inspector draft remain synchronized throughout the host change. Overlay and Separate Window never show another presentation dropdown: their return control always goes directly back to Embedded. The normal page-area hide/show control also appears only in the embedded editor and remains synchronized with the Runtime Graph.

The large editor and the small Properties code field synchronize in both directions on every input, including after selecting other nodes and returning, or after moving the editor between embedded and overlay presentation. Click a compatible node in the left palette while an editor is active, drag a palette node onto the editor, or drag an existing graph node onto it to insert the node's C# representation at the caret. Unsupported nodes are rejected without changing their graph position or source.

Find, Replace and Settings are real toggle buttons: their pressed state is visible, a second click closes the same panel, and opening one closes the conflicting panel. Find supports Match Case, Whole Word and Regular Expression, previous/next navigation, Replace and Replace All. Every active match is the textarea's real focused forward selection, not a visual overlay, so navigation and replacement leave the exact source range selected.

Live debug & problems

Builder and Roslyn are separate output sources

In Editor Settings choose either Builder or Roslyn. Debug and Problems render only the selected source; the other source remains available but is never mixed into the visible list. Builder reports generation, synchronization and worker activity. Roslyn reports live C# 14 syntax diagnostics. Switching sources redraws both views immediately.

Diagnostics refresh while code is typed and after editor/graph synchronization. If the same error occurs again, its newest occurrence replaces the older visible record with a fresh monotonic millisecond timestamp instead of being discarded as a duplicate. This applies independently to Builder and Roslyn, so repeated status and error messages always show when they most recently occurred.

Harmony load phases

Main mod patches and early rml_libs patches

Harmony Patch Event, lifecycle patch presets and scanner-generated Harmony API calls stay in the main mod project. They are registered when the mod reaches OnEngineInit, because their callbacks may emit graph impulses and access generated runtime state.

Harmony Exact Patch Source also stays in the main project, but its attribute patches are now registered automatically with one guarded PatchAll call. Use Early Harmony Patch Library (rml_libs) only when a patch must be active before normal rml_mods are loaded. That node creates an independent project and DLL and cannot depend on graph sockets or main-mod configuration state. It can only target assemblies already available before rml_mods are loaded; patches for another normal mod belong in the main mod phase. Automatic discovery of the early DLL requires the matching special Builder-compatible Mod Loader build containing the generated-library marker support.

Low-level HarmonyLib nodes produced by the API scanner are kept under Advanced / Raw C#. They expose the scanned API but do not infer patch signatures, callback methods or load phase automatically.

Builder-owned Harmony patches receive one idempotent Harmony-specific shutdown routine. It calls UnpatchAll for the generated Harmony id during runtime drain and process shutdown. This routine is generated only when the graph actually creates the Builder's Harmony runtime; Harmony-free mods contain neither that code nor the 0Harmony.dll reference. Every actual Harmony dependency remains explicitly excluded from live reload.

Expert fallback

Advanced / Raw C# and the hybrid Custom C# node

Manual usings, references, source files, compiler overrides and reflection-oriented fallback nodes stay hidden unless Show Advanced / Raw C# is enabled. Prefer normal typed catalog nodes whenever a direct node exists.

Custom C# itself is one hybrid node, not five separate palette entries. File mode owns a persistent visual C# File Graph; Action and Expression expose typed graph ports; Runtime Graph Member and Main Mod Member emit complete member declarations into their respective generated classes. C# Project defines an optional compiled project and C# Reference switches between Assembly, NuGet Package and Framework references. These three nodes are also supported inside an API & Logic Graph.

Opening File mode's Node Graph exposes the isolated C# 14/Roslyn syntax library and its Custom C# File Output. Those syntax-building nodes never appear in the main Runtime Graph or directly in an API & Logic Graph. The Nodes page marks every restricted node and builds the complete fixed registry reference at runtime, including palette-hidden helpers.

Builder environment

Required, conditionally required and optional

The web Builder, the generated project toolchain and the Resonite runtime are separate layers. Install only the layer needed for the intended task.

Required To run a compiled Builder mod: a compatible 64-bit Resonite installation, the special Builder-compatible Mod Loader and dependencies supplied by the Builder author, and the generated mod DLL plus its exported library dependencies.
Build Additionally required to compile a Builder export: the .NET 10 SDK and access to the matching Resonite and special-loader reference assemblies selected by the generated project.
Conditional The live Scanner is required only when a project imports, validates or exports version-derived Resonite, FrooxEngine or Harmony API catalog nodes.
Optional Window-pinning utilities, Git and an external IDE can improve the workflow but are not required by the generated mod.
Required to use generated mods

Resonite, the private Builder loader and exported DLLs

Install a compatible 64-bit copy of Resonite. The officially published minimum desktop requirements currently start at Windows 10, a dual-core CPU, 8 GB RAM, a GTX 750-class GPU, DirectX 11, broadband internet and 2 GB free storage; VR needs additional headroom.

Use only the exact special Builder-compatible Mod Loader package supplied privately by the Builder author through a Discord Direct Message. Install every dependency included with that package and use its supplied launch configuration. Do not replace or update it with the public standard loader, Resolute or another generic mod manager; those versions can be incompatible with Builder-generated functionality.

Place the generated mod assembly in rml_mods, and place exported non-framework dependency assemblies in rml_libs. Start Resonite and verify the special loader and mod entries in the Resonite logs. Loader updates must come from the Builder author through the same private Discord Direct Message distribution path.

The special loader already provides its own settings page. An external settings mod such as ResoniteModSettings is not required and must not be assumed compatible unless the Builder author's documentation explicitly confirms the exact combination.

Someone who only installs an already compiled mod does not need the .NET SDK, a source-code editor, Git, the Builder Scanner or a window-pinning utility. There is intentionally no public loader download link here because the Builder requires its privately supplied version.

Required to compile Builder exports

Install the .NET 10 SDK and resolve game references

Building an exported net10.0 project locally requires the .NET 10 SDK. The runtime alone can execute compatible applications but cannot compile the generated project. Installing the SDK also installs its matching runtime, so a separate runtime installation is normally unnecessary.

Windows Run winget install Microsoft.DotNet.SDK.10, or use the official Windows instructions.
macOS Use the Microsoft installer matching Apple silicon (Arm64) or Intel (x64): Install .NET on macOS.
Linux Use the package instructions for the installed distribution: Install .NET on Linux.
Verify Open a new terminal and run dotnet --list-sdks. At least one line must begin with 10.0.; use dotnet --info when diagnosing architecture or path problems.

Direct installers for all supported systems and architectures are also available on the official .NET 10 download page.

The generated project must also resolve the Resonite, FrooxEngine, Elements.Core and special Builder-compatible Mod Loader assemblies it references. Keep the generated project beside the exported rml_mods and rml_libs structure, or set its documented ResonitePath override to the correct local installation before running dotnet build.

Conditionally required

Use the live Scanner for version-derived API nodes

The fixed Builder nodes, Configuration Outline, Custom C# editing and projects without catalog-derived API nodes do not require a Scanner. A live compatible Scanner becomes mandatory when the project uses the generated Resonite, FrooxEngine or Harmony API catalog: the Builder verifies the running installation's semantic catalog and fingerprint before import, replacement or export. A cached catalog is useful for display but is not a substitute for live verification when those API contracts must be emitted.

Start the Scanner supplied for the Builder environment, keep its local health endpoint reachable, and wait for the Builder's catalog source to show a verified live state. Do not expose the Scanner port to the internet; it is a local development companion rather than a public service.

Windows 10 / 11

Microsoft PowerToys provides the system-level Always On Top function. Focus the separate editor and press Win + Ctrl + T. Press the same shortcut again to unpin it. The optional border, sound and shortcut can be changed in PowerToys settings.

macOS

Use Overlay, Split View or optional window pinning

macOS has no universal built-in Always On Top switch for arbitrary browser windows. Use the Builder Overlay for guaranteed in-tab priority, or place the Builder and separate editor side by side with Apple Split View.

Users who specifically need system-wide pinning can evaluate a third-party window utility such as WindowPin on the Mac App Store. This is optional third-party software, not a Builder dependency.

The web Builder and the .NET 10 SDK can be used on macOS for authoring and compilation. Running the resulting mod still requires an operating system, Resonite installation and mod-loader combination supported by those runtime projects; a window utility does not change that runtime compatibility.

Linux desktops

Use the desktop environment's window rule

On KDE Plasma, use Keep Above from the window menu or create a KWin rule for the editor window. KDE documents the corresponding Keep above window attribute.

GNOME users can use the desktop's available window action or the optional Window on Top GNOME extension. Under X11, wmctrl -r :ACTIVE: -b toggle,above can toggle the active EWMH-compatible window. Under Wayland the compositor controls this capability, so KDE/GNOME window actions are preferable to X11 commands.

The Builder and .NET 10 SDK are cross-platform, but running Resonite and the special Builder-compatible Mod Loader on Linux must follow the private package's compatibility notes and the selected Steam compatibility setup. Verify the loader logs before treating a generated mod failure as a Builder failure.

Chrome, Edge, Firefox & Safari

Allow pop-ups for Separate Window

Use a current Chrome, Edge, Firefox or Safari release with JavaScript, WebAssembly, browser storage and file downloads enabled. These capabilities are required for the complete Builder workflow; pop-up permission is needed only for Separate Window.

Separate Window uses a normal browser popup. If nothing opens, allow pop-ups for the Builder site and try again. The editor does not request Picture-in-Picture, simulate maximization or draw a second set of native window controls. Search, diagnostics, settings, node insertion and the small Inspector code field remain synchronized in Embedded, Overlay and Separate Window modes.

Browser and operating-system window behavior can differ. Overlay remains the portable fallback whenever pop-ups, multiple displays or desktop pinning are unavailable; Separate Window remains the practical choice for placing the editor on a second display.

Builder node libraries

Node reference

Configuration Outline nodes define the generated RML settings menu: stored controls, impulse buttons, runtime display rows and structural containers. Their order and nesting are the menu layout.

Click a palette node to add it to the active container, or drag it to an exact position. Every palette tooltip now describes the resulting menu control instead of repeating the visible badge and plus symbol.

This is the complete reference for the builder's fixed built-in Runtime Graph nodes, including palette-hidden helper nodes. Advanced / Raw C# nodes remain deliberately separated from normal typed nodes.

Custom C# appears once as a hybrid node whose Mode selects File, Action, Expression, Runtime Graph Member or Main Mod Member. C# Project and C# Reference remain advanced nodes. All three are usable in the Runtime Graph and inside an API & Logic Graph; Roslyn syntax/token/trivia nodes are marked Custom C# File Graph only.

Catalog-generated Resonite API nodes are version-derived rather than fixed builder nodes. Their collapsed categories and complete counts are always visible in the Node Library; opening one loads safe batches, while Node Search remains the fastest direct lookup for a generated Type, Enum, Constructor, Method, Property, Field or Event node.

Start / Configuration

Outline Button impulse outputs

Every Button (Impulse) placed in Configuration Outline becomes one stable direct Impulse output on the packed Start node. Connect it to Branch, Sequence, method calls, stores, runtime menu actions or any other impulse input. The generated RML button invokes that exact output once per press. Visibility and absolute order remain controllable through the Configuration Menu nodes.

Configuration Menu

Inline row layout, width and labels

Every Inline row is exposed as a stable Menu Item on Configuration Menu Instance. Connect that output to Set Configuration Visibility to override the row's static Internal / hidden state, or to Set Configuration Layout and drive Horizontal with a Boolean to switch the open RML menu between side-by-side and stacked layout at runtime. Connect a direct child item to Set Configuration Width to override its percentage, or to Set Configuration Label Visibility to show or hide only its left-side label. The same outputs also work with Set Visibility, Set Order and Reset Configuration Item. Rebuilding preserves unsaved editor drafts. The connected action path is also simulated in Preview, so these changes are visible immediately there while remaining completely local; no Preview layout action is sent to Resonite.

Save Configuration Settings is an Impulse action for Outline buttons. It first captures the values currently typed into the open RML menu, validates and persists them, then emits Done. Connect subsequent actions to Done so a button can save its sibling text field before rebuilding or changing the menu. Failed handles a missing menu, invalid input or a save error. Preview performs the same sequence against its browser-local draft only and never synchronizes it to Resonite.

Dynamic settings

Collection-backed Dynamic Choice

A Collect To List node marked Editable contributes one generated Dynamic Choice entry to the Configuration Outline palette. The entry is only a creation option until you explicitly click or drag it.

Once placed in the Outline, the control uses the marked runtime collection as its only option source and is emitted as a normal typed Start / Configuration output after packing. No Labels/Stable Values monitor selection is needed. A Default selection can only be picked while the matching generated mod is running and the runtime list is available. The direct runtime subscription refreshes Properties and Preview immediately when that list changes; otherwise the first runtime item is used automatically unless empty selection is explicitly allowed. The Start-node value follows that effective runtime selection immediately when the collection changes. The control keeps its exact global Outline position among normal settings and Runtime Display rows. No setting is auto-inserted merely by enabling Mark as Editable.
